01 / WHAT TEAM6 IS

A governed team,
instantiated from one parameter file.

Team6-kit defines role lanes with identity archetypes so each agent has a fixed mandate, choreography for how orchestrators and workers hand work to each other, governance rules and phase gates so nothing ships past an unsigned review, knowledge routing that keeps persistent memory small enough to fit a bounded context, and provenance enforcement where every source file carries a manifest verdict and an unclassified file fails the build.

ROLE LANES

Identity archetypes, fixed mandates

Each agent has one lane with a defined role, so a team is a set of distinct mandates rather than a crowd of interchangeable prompts.

ORCHESTRATION

Choreography with defined hand-offs

Orchestrators and workers pass work through explicit choreography, so supervision is a designed stage, not an afterthought.

GOVERNANCE

Rules and phase gates

Phase-gated orchestration means nothing ships past an unsigned review. Disciplined by structure, not by vigilance.

STATE & MEMORY

Durable state and bounded context

Knowledge routing keeps persistent memory small enough to fit a bounded context, so a long-running team does not drift into a bloated, contradictory past.

PROVENANCE

Served-truth verification

Every source file carries a manifest verdict and an unclassified file fails the build. What is claimed is what is served, and what is served is what is checked.

GENERATOR

One file assembles a team

A generator is the only assembly path: it instantiates a full configured team from a single parameter file, and the repository ships a frozen-clone proof point so a stranger can reproduce the instantiation from a clean clone.

Built on the Hermes engine. The kits layer is Apache-2.0. Current release: v1.2.0.

02 / LOCAL PREPROCESSING

Small specialist models
around the team, not instead of it.

Team6 can use a guarded local preprocessing layer when a narrow task does not need a large reasoning model. Redact can prepare approved outbound text and hold address or uncertain findings for review. Gist can provide cheap topic hints for bulk intake. Title can draft metadata for artifacts and transcripts.

PRIVACY

Local first-pass redaction

Sensitive text can be screened on-device before an approved outbound step. The filter is not legal anonymization; uncertain and address-related findings stop for review.

EFFICIENCY

Cheap hints and metadata

Topic hints and draft titles reduce repetitive work before Team6 performs interpretation, judgment, and final synthesis.

The layer is automatic when the workflow benefits from it, but bounded: it does not replace Team6 reasoning, make high-stakes decisions, route solely on a small model, or download media models during active work. Model licensing remains separate from the Apache-2.0 kits layer.

03 / THE MODEL STACK

Different models.
Different jobs. One governed system.

Team6 is designed to route across a spectrum rather than worship a single model. Frontier cloud models handle difficult synthesis and broad reasoning when the approved environment allows it. Local quantized midrange models handle repeatable work near the data. Specialized local models handle narrow transformations. Experimental local variants, including abliterated builds where appropriate, are treated as bounded technical options — not as magic — and remain subject to evaluation, provenance, licensing, and safety gates.

FRONTIER CLOUD

deep synthesis · architecture · difficult judgment

↓ routed by task, privacy, cost, and capability
LOCAL QUANTIZED MIDRANGE

private work · repeatable analysis · lower-latency execution

↓ narrow task boundary
LOCAL SPECIALISTS

redaction · topic hints · titles · media-specific transformations

The point is not maximum model count. The point is matching capability to the job while preserving a reviewable chain of custody. Models are replaceable. Routing policy, role separation, provenance, durable state, and verification are the durable asset.

04 / HOW ASKA USES IT

Governed operating practice,
not ad-hoc chat.

For ASKA, Team6-kit is the shared layer underneath the firm’s own agent work. Agent teams run on it as governed operations — with role lanes, phase gates, durable state, and provenance — rather than as a scatter of one-off conversations. It is open source on purpose: the engine stays upstream and unmodified, the kits layer is Apache-2.0, and vertical packs remain proprietary by contract. What is public is the general method, not any client deployment.

05 / THE BOUNDARY

What this kit is,
and is not.

ASKA keeps the honest read on the page with the project. Three lines hold it.

Portfolio, not a case study. Team6-kit is an open-source ASKA portfolio project. It is not a client case study, and no client name, engagement, or outcome is attached to it.

Breadth, not vertical proof. The public kit is the operating layer ASKA uses for multi-agent work. It does not by itself prove performance in any specific vertical; vertical deployments run through proprietary pack parameters and services that are not part of the public repository.

“Largest” defined honestly. ASKA calls it the largest open-source portfolio project by the breadth of the system’s surface — identity, orchestration, governance, memory routing, build gates, and the generator — and by its role as the shared layer under ASKA’s agent work. Not by star counts, file counts, or lines of code.
